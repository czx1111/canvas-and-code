## TSL（自旋锁）

### 底层原子动作

TSL 指令在执行时，CPU 会**锁住内存总线**，然后在一个 CPU 周期内连续完成：

- 读 `lock` 的旧值
- 无条件将 `lock` 写为 1
- 返回旧值

这三步被打包成**一条不可分割的原子指令**，不存在"刚读完 0 还没写 1，另一个 CPU 也读到 0"的窗口。

### 互斥实现过程

**抢锁**：进程 A 执行 `while(!TSL(&lock)){}`，如果 `lock=0`（空闲），TSL 读到 0，立刻把 `lock` 改成 1，返回 0，`!0` 为真，**A 进入临界区**。

**占锁**：此时内存中 `lock` 已经变成 1。

**等锁**：进程 B 执行 TSL，读到 1，把 1 重新写回 1（覆盖），返回 1，`!1` 为假，**B 被拦在门外，死循环原地打转**——这就是"自旋"。

**解锁**：A 执行 `lock = FALSE`（普通赋值），把内存值改回 0。B 下一次 TSL 才能读到 0，抢锁进入。

> TSL 通过**硬件总线锁**保证了"检查并上锁"的绝对原子性，任一时刻只有一个进程能"逮到"0 并通过临界点。

## 信号量（PV 操作）

信号量是操作系统提供的数据结构（包含一个 `value` 值和一个进程等待队列）。它的原子性不是靠硬件总线，而是靠**操作系统内核把 PV 操作定义为系统调用（原语）**。

### 底层原子动作

当进程调用 `P(S)` 或 `V(S)` 时，会陷入内核态。操作系统**在执行 PV 操作的过程中暂时屏蔽中断**（或底层用 TSL 保护），确保 `value` 的增减和队列操作**一气呵成，绝不打断**。

### 互斥实现过程

**初始化**：`S.value = 1`（一个资源可用），等待队列为空。

**P 操作（申请）**：
- 进程 A 调用 `P(S)`，内核原子执行 `S.value--`（变为 0）
- 判断 `S.value < 0`？不小于（等于 0），资源抢到了，**A 进入临界区**

**V 操作（释放）**：
- A 退出临界区后调用 `V(S)`，内核执行 `S.value++`（变为 1）
- 判断 `S.value <= 0`？不大于，没有进程排队，直接结束

**竞争场景**：
- A 在临界区内，B 调用 `P(S)`
- 内核执行 `S.value--`（从 0 变为 **-1**）
- `S.value < 0` 为真！内核**立刻将 B 挂起，放入等待队列**，调度器把 CPU 让给其他进程（**真正的让权等待**）
- A 退出后调用 `V(S)`，`S.value++`（从 -1 变为 0），发现 `S.value <= 0`，**唤醒 B 置为就绪态**

> 信号量通过**操作系统强制执行的原子性操作**，将"资源数减 1 并判断是否小于 0"作为一个整体，把抢不到资源的进程**物理地挪出 CPU**。

## 伪代码对照

| 伪代码 | 等价操作 | 底层原子的是什么 |
| :--- | :--- | :--- |
| `while(!TSL(&lock)){}` | **P 操作（申请）** | 只有 `TSL(&lock)` 这条读-改-写指令是原子的。外面的 `while` 循环和判断逻辑**不是原子的** |
| `lock = FALSE` | **V 操作（释放）** | 只是一条**普通赋值语句**，不具备 TSL 的硬件锁总线能力，多核下可能涉及缓存一致性协议 |

## 为什么信号量底层也需要 TSL？

既然 PV 操作是内核原语，内核怎么保证自己修改 `S.value` 时不被中断打断？

- **单核 CPU**：PV 操作一开始执行**关中断**指令，操作完再**开中断**
- **多核 CPU**：关中断只能关掉当前 CPU 核，其他核依然能访问 `S.value`。所以操作系统底层**依然借用 TSL（或 CAS 指令）**来保护 `S.value`

## 管程（Monitor）：编译器的贴心管家

TSL 靠硬件野蛮抢锁，信号量靠操作系统精确排队，而**管程（Monitor）则完全上升到了编程语言层面**——它让**编译器**去处理加锁解锁的脏活累活。

### 什么是管程？

管程是一种**高级程序设计语言结构**（如 Java 的 `synchronized` 关键字），它将共享资源、操作函数和同步逻辑封装在一起。**编译器会自动在管程里每个函数的入口处插入加锁指令，在出口处插入解锁指令**。

> 程序员再也不用手写 `while(!TSL)` 或配对 `P/V` 了，彻底杜绝了"忘记解锁"和"PV 顺序颠倒"的编程错误。

### 管程如何实现互斥？

管程内部维护了一把隐式锁。当进程 A 调用管程中的函数时，编译器插入的加锁代码会让 A 获得锁。如果此时进程 B 也想进来，它会被**挡在管程入口的等待队列**里，直到 A 执行完函数并自动释放锁。

### 管程如何实现同步？（条件变量）

互斥解决了"同时进多人"的问题，但解决不了"顺序"问题（比如缓冲区满了，生产者必须停手）。管程提供**条件变量（Condition Variable）**及其配套操作 `wait()` 和 `signal()`。

**标准同步模板（以生产者为例）**：
```c
monitor Buffer {
    condition notFull;
    int count = 0;

    procedure produce(item) {
        // ① 一进函数，编译器自动加锁
        
        while (count == 10) {      // 条件不满足（满了）？
            notFull.wait();        // ★ wait()：释放锁 + 阻塞自己 ★
        }
        // ③ 被唤醒并重新抢到锁后，继续执行
        count++;
        notFull.signal();          // ④ 通知消费者
        // ⑤ 函数结束，编译器自动释放锁
    }
}
```

### 管程的两个核心机制

**机制一：`wait()` 的原子性**
当进程执行 `condition.wait()` 时，该操作**原子性地**完成两件事：
1.  **立刻释放当前管程锁**（如果不释放，别人进不来改条件，必将死锁）；
2.  阻塞当前进程，放入该条件变量的等待队列。

**机制二：`signal()` 与 PV 中 `V` 的天壤之别**
这是最易混淆的考点：
- **PV 中的 V 操作**：有"记忆效应"。即使没有进程等待，执行 `V` 也会让 `S.value++`，代表多出一个资源。
- **管程中的 signal**：**没有记忆效应**。如果条件变量的等待队列为空，执行 `signal` 就相当于"喊了一嗓子但没人听见"，瞬间消失，不改变任何变量。

> 正因为 `signal` 没有记忆性，且被唤醒后锁可能被其他进程抢走，管程编程的铁律是：**必须用 `while(条件不满足)` 包裹 `wait()`，绝对不能用 `if`**（防止虚假唤醒后条件又被改变）。

## 终极对比：TSL / 信号量 / 管程

| 对比维度 | **TSL（自旋锁）** | **信号量（PV）** | **管程（Monitor）** |
| :--- | :--- | :--- | :--- |
| **实现层次** | 硬件（CPU指令） | 操作系统（内核原语） | **编程语言（编译器/运行时）** |
| **互斥的保证者** | 程序员手动写 `while` | 程序员手动写 `P/V` | **编译器自动在函数入口/出口加解锁** |
| **等待机制** | 忙等待（死磕CPU，不满足让权等待） | 阻塞等待（挂起，让出CPU） | 阻塞等待（挂起，让出CPU） |
| **同步（条件等待）工具** | 无（仅靠轮询） | 信号量整型值计数 | **条件变量 + wait / signal** |
| **signal / V 的区别** | — | V 操作**累加**资源数（有记忆） | signal **空操作**（无记忆，无人等则丢失） |
| **唤醒操作执行者** | 无（解锁仅赋值，未阻塞则不唤醒） | V 操作由内核唤醒阻塞进程 | signal 由编译器生成的代码触发内核调度 |
| **程序员出错风险** | 极高（易忘解锁） | 较高（PV 配对易颠倒） | **极低（结构强制规范，编译器兜底）** |
