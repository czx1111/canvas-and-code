## 基础概念层

在计算机组成原理与操作系统中，CPU 对外部或内部事件的响应分为两大类：

### 异常（Exception）—— 内部中断

- **触发源**：CPU 执行指令时内部触发
- **同步性**：**同步**（与当前指令绑定）
- **子类**：
  - **故障（Fault）**：可恢复（如缺页），修复后**重新执行**该指令
  - **陷阱（Trap）**：主动请求（即系统调用），执行后**返回下一条指令**
  - **终止（Abort）**：致命错误（硬件崩），无法恢复

### 中断（Interrupt）—— 外部中断

- **触发源**：硬件设备随机发出电信号
- **同步性**：**异步**（与当前指令无关）
- **子类**：
  - **可屏蔽中断**：受 CPU 的 `IF` 标志位控制，用于普通 I/O 设备
  - **不可屏蔽中断（NMI）**：不受 `IF` 控制，用于内存校验错、电源掉电等紧急救命场景

## I/O 请求全生命周期

> **实验环境假设**：x86-64 架构，Linux 内核，用户进程发起 `read()` 文件操作。

下面将**流程步骤**与**"硬件保存什么、操作系统保存什么"**无缝融合，展示每一次状态切换背后的底层栈操作。

### ① 发起系统调用

- **CPU 模式**：用户态 → 内核态
- **动作**：进程执行 `int` 或 `syscall` 指令，触发**陷阱（Trap）**
- **硬件自动保存**：
  - 切换栈：从 TSS 段读取**内核态 SS 和 RSP**，压入旧用户态 SS/RSP
  - 压入 `RFLAGS`、`CS`、`RIP`（返回地址）
  - 硬件自动**关中断**（清 `IF`，防止嵌套）
- **操作系统保存**：内核入口汇编（如 `entry_64.S`）将**所有通用寄存器**（RAX, RBX, RCX, RDI, RSI, RBP, R8-R15 等）及段寄存器压入内核栈，封装为 **`pt_regs`**，并将系统调用号传给 C 函数

### ② 驱动配置与休眠

- **CPU 模式**：内核态（进程上下文）
- **动作**：驱动程序配置 DMA 寄存器（内存地址、字节数），向设备控制器发"开始"指令。调用 `wait_event_interruptible()`，当前进程置为**阻塞态**，让出 CPU
- **硬件**：此阶段无中断发生，硬件不干预
- **操作系统**：保存该进程的**内核栈指针**和**进程描述符（task_struct）** 状态，将其移出运行队列

### ③ DMA 数据搬运

- **CPU 模式**：**CPU 完全旁观**
- **动作**：外设通过 DMA 控制器将数据直接搬入**内存缓冲区**，无需 CPU 干预
- **硬件 / OS**：均无操作

### ④ 设备发送中断

- **CPU 模式**：外设硬件
- **动作**：数据搬运完毕，设备控制器向中断控制器（APIC）发送**可屏蔽外部中断**信号
- **硬件**：中断信号挂起，等待 CPU 响应
- **操作系统**：未触发软件处理

### ⑤ CPU 响应与硬件自动压栈

- **CPU 模式**：内核态（可能打断任意代码）
- **动作**：CPU 在**当前指令边界**检测到中断，决定响应。**注意：如果当前已在内核态，则不切换栈（不压入 SS/RSP）**
- **硬件自动保存**：
  - 若中断前是用户态，则切栈并压入旧 SS/RSP（同步骤①）
  - **必压**：`RFLAGS`、`CS`、`RIP`
  - 硬件自动**关中断**（清 `IF`）
  - 根据中断向量号查 IDT，跳转到 ISR 入口
- **操作系统**：此时软件尚未执行

### ⑥ 操作系统保存现场

- **CPU 模式**：内核态（中断上下文）
- **动作**：跳转到中断入口汇编，**此时所有通用寄存器仍残留旧数据**，必须立即保存
- **硬件**：保存已结束
- **操作系统**：汇编代码将**所有通用寄存器**（RAX, RBX, RCX 等）和**段寄存器**再次压入**当前内核栈**，形成新的 `pt_regs` 帧（与前一层 `pt_regs` 串行共存）。将中断向量号和硬错误码传递给 C 函数 `do_IRQ()`

### ⑦ 执行 ISR（上半部）

- **CPU 模式**：内核态（中断上下文，**无进程概念**）
- **动作**：C 语言中断服务程序执行：
  - ① 读设备状态确认
  - ② 向中断控制器发 **EOI（结束中断）**
  - ③ 调用 `wake_up()` 唤醒阻塞进程（移至就绪队列）
  - **（绝不在此处处理数据）**
- **操作系统**：修改进程描述符（`task_struct`）状态为**就绪态**

### ⑧ 软中断 / 下半部（可选）

- **CPU 模式**：内核态（软中断/内核线程）
- **动作**：为快速返回，耗时的数据处理（如网络协议栈）交给下半部异步处理
- **操作系统**：调度软中断线程或工作队列执行

### ⑨ 中断返回与现场恢复

- **CPU 模式**：内核态 → 原态
- **动作**：ISR 结束，执行 `iret` 指令
- **硬件**：自动弹出栈中的 `RFLAGS`、`CS`、`RIP`；若原先是用户态，还会弹出 `SS` 和 `RSP`，**自动开中断**（恢复原 `IF` 值）
- **操作系统**：在 `iret` 之前，汇编代码**逆序弹出**所有通用寄存器和段寄存器（恢复 `pt_regs`），完美还原被打断的现场

## 核心机制层

### 1. 中断上下文 vs 进程上下文（生死红线）

- **中断上下文（ISR 上半部）**：不关联任何进程，`current` 指针无效。**绝对禁止调用 `schedule()` 或睡眠**（如 `kmalloc(, GFP_KERNEL)`），因为无可切换的进程实体。这也是为什么中断栈通常只有几 KB
- **进程上下文（系统调用）**：关联当前进程，可以睡眠、可以缺页、可以主动调度

### 2. 中断嵌套与关中断机制

- 硬件响应中断时**默认自动关中断**（清 `IF`），这意味着在默认 Linux 设置下，**中断服务程序通常不支持嵌套**（除非 ISR 内主动开中断，极不推荐）
- 但现代中断控制器（如 APIC）支持优先级：高优先级中断可抢占低优先级（需配置 `IRQF_DISABLED`，但现代内核已简化）

### 3. 中断下半部（Bottom Half）的设计哲学

- **上半部（Top Half）**：即 ISR，必须快进快出，只做最紧急的硬件应答和唤醒
- **下半部（Bottom Half）**：将耗时的数据处理（如网卡数据包解析）延后至**软中断（Softirq）**、**Tasklet** 或**工作队列（Workqueue）** 中执行，确保 CPU 能及时响应下一个外部中断，避免丢包

## 硬件 vs 操作系统"保存分工"的设计哲学

### 硬件（CPU）负责保存

保存内容：`RIP`、`CS`、`RFLAGS`、`SS`/`RSP`（切换栈时）、硬错误码

**为什么必须由硬件负责？**

1. 只有硬件知道当前**指令执行的精确边界**（原子性）
2. 栈切换涉及**特权级变更**（TSS 段读取），软件无权干预
3. 保证原子性，防止切栈过程中被干扰

### 操作系统（软件）负责保存

保存内容：所有通用寄存器（`RAX~R15`）、段寄存器（`DS`、`ES` 等）

**为什么必须由操作系统负责？**

1. 数量多且随 CPU 架构演进（如 AVX 寄存器），硬件固化不灵活
2. 操作系统知道**哪些寄存器后续 C 代码会污染**，按需保存，可优化性能
3. 封装为 `pt_regs` 结构体，便于 C 函数统一访问

> **记忆口诀**：**硬件压栈保来路（RIP/CS/标志/栈），关中断防嵌套；软件汇编保家底（通用寄存器全拉满），`iret` 一弹原路返。**

## 脑图

```
【用户态进程】
   │ read()
   ▼ ① 陷阱(Trap) — 硬件自动保存：SS/RSP(切栈)、RFLAGS、CS、RIP；OS保存：通用寄存器(pt_regs)
【内核态（进程上下文）】
   │ 配置DMA、启动设备、进程阻塞(休眠)
   ▼ ② CPU让出，DMA自主搬运数据（CPU旁观）
【硬件完成】
   │ ③ 发送外部可屏蔽中断
   ▼ ④ CPU响应（若原先在内核态，不切栈）— 硬件自动保存：RFLAGS、CS、RIP；OS保存：通用寄存器(新pt_regs帧)
【内核态（中断上下文，无进程）】
   │ ⑤ ISR执行（关中断）：读状态、发EOI、wake_up()
   ▼ ⑥ 触发下半部（软中断/工作队列）处理耗时任务
【中断返回】
   │ ⑦ OS恢复通用寄存器；硬件执行iret自动弹出RFLAGS、CS、RIP（及用户态SS/RSP）
   ▼ ⑧ 进程被调度，从read()返回，拿到内存数据
【用户态进程】继续执行
```

> 一句话总结：**异常同步绑定指令、中断异步来自外设；硬件保来路（RIP/CS/RFLAGS/栈），软件保家底（通用寄存器）；中断上下文不可睡眠，进程上下文方可调度。**
